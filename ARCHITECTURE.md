# Архитектура MVP v0.4
_31.08.2026_

## Пайплайн
Источники → нормализация → дедуп/кластеризация → фильтр релевантности интересам и
рекламы/шума (один LLM-вызов на кластер) → суммаризация прошедших кластеров → доставка
(Telegram-канал)

Архитектурный стиль — **модульный монолит с двумя runtime-компонентами из одного
Python-пакета**:

1. `pipeline-runner` — конечная CLI-команда: запускается по cron в GitHub Actions,
   выполняет один прогон, сохраняет контрольные точки и завершается;
2. `bot-worker` — постоянно работающий процесс с непрерывным Telegram long polling:
   сразу обрабатывает кнопки и команды управления источниками/интересами.

Оба компонента используют один отдельный Neon Postgres-проект AI News Feed через общий
интерфейс `Repository`. Очереди и микросервисы для MVP не нужны: коннекторы,
LLM-провайдер, хранилище и доставка скрыты за небольшими интерфейсами, поэтому их можно
менять независимо от доменной логики.

## Зафиксированный язык и стек

**Выбор: Python 3.12.** Это не только самый короткий путь, но и наименее рискованная
стыковка уже выбранных компонентов:

- Telethon, SemHash, Model2Vec, `pdfplumber`, `python-docx`, `feedparser` и
  `trafilatura` — нативные Python-библиотеки; не понадобится отдельный сервис или FFI
  вокруг каждого шага;
- все CPU-тяжёлые операции внутри этих библиотек выполняются в оптимизированных
  зависимостях, а объём одного личного дайджеста мал, поэтому производительность самого
  Python не является ограничением;
- Python 3.12 поддерживается SemHash (минимум у него — 3.10) и доступен на GitHub Actions;
- тот же язык покрывает коннекторы, извлечение документов, ML и Telegram Bot API, что
  уменьшает число сборок и объём поддержки для соло-проекта.

Фреймворк уровня Django/FastAPI не нужен: у MVP нет HTTP API или веб-интерфейса, а бот
работает через long polling. Оркестрация — обычные Python-модули с `asyncio` и двумя
CLI-точками входа; расписание пайплайна остаётся снаружи в GitHub Actions. Это позволяет
использовать асинхронные Telethon, Bot API, HTTP и Postgres, не добавляя Airflow/Celery.
Если позже появится webhook или UI, HTTP-адаптер можно добавить поверх тех же сервисов.

Базовый набор:

| Задача | Выбор для MVP | Почему |
|---|---|---|
| Проект и зависимости | `pyproject.toml` + `uv`, зафиксированный `uv.lock` | Быстрая воспроизводимая установка локально и в CI |
| Контракты и конфигурация | Pydantic v2 + `pydantic-settings` | Валидация входов коннекторов и структурированного JSON от LLM |
| HTTP/RSS/статьи | `httpx`, `feedparser`, `trafilatura` | Один HTTP-клиент, зрелый разбор фидов и извлечение основного текста |
| Telegram-источники | RSS-Bridge через HTTP; Telethon для fallback и вложений | Простые каналы не требуют своего парсера, сложные остаются доступны |
| PDF/DOCX | `pdfplumber`, `python-docx` | Уже выбранный лёгкий путь без OCR; сканы пока помечаются как ошибка извлечения |
| Дедуп | `hashlib`/нормализация + SemHash/Model2Vec | Сначала почти бесплатный точный фильтр, затем локальная семантика |
| LLM | Собственный тонкий `LLMClient` над SDK выбранного API | Не связывать домен с провайдером и не тянуть LangChain ради двух промптов |
| Bot API | `python-telegram-bot`, непрерывный long polling | Асинхронные handlers, немедленная реакция в личке и готовая отправка сообщений без публичного HTTP endpoint |
| Хранилище | отдельный Neon Postgres 18 по TLS через SQLAlchemy 2 Core + `psycopg` 3; Alembic для миграций | Одно долговечное состояние для bot-worker и cron, полностью изолированное от БД `rus-ai.com` |
| Качество | `pytest`, `ruff`, `mypy` | Быстрые тесты, формат/линт и проверка контрактов в CI |

Альтернативы, которые рассмотрены, но не выбраны:

- **TypeScript**: сильная типизация и удобный Bot API, но Telethon, SemHash и
  `pdfplumber` пришлось бы выносить в Python-сервис. Для MVP это два рантайма и лишняя
  граница отказа.
- **Go**: хороший единый бинарник и дешёвый запуск, но выбранный ML/document stack всё
  равно остаётся в Python; экономия рантайма не окупает обвязку.
- **LangChain/Airflow**: дают провайдерские интеграции и DAG UI, но для линейного
  расписанного прогона добавляют большой граф зависимостей и инфраструктуру. Тонкие
  интерфейсы и GitHub Actions покрывают текущий сценарий.

## Структура Python-проекта

```text
pyproject.toml
alembic/                       # версионируемые миграции Postgres
.github/workflows/pipeline.yml # cron: pipeline-runner только на GitHub runner
deploy/systemd/
  ai-news-feed-bot.service     # отдельный unit-шаблон для VPS
src/ai_news_feed/
  domain/models.py             # типы данных и инварианты, без I/O
  config.py                    # настройки из env/БД
  sources/base.py              # протокол SourceConnector
  sources/rss.py               # нативный RSS + выдача RSS-Bridge
  sources/telegram.py          # Telethon
  sources/manual.py            # ссылка/forward, присланные боту
  extraction/articles.py       # HTML -> основной текст
  extraction/documents.py      # PDF/DOCX -> текст
  normalization.py             # RawItem -> Material
  dedup/exact.py               # external id, URL и content hash
  dedup/semantic.py            # SemHash и сборка кластеров
  screening.py                 # релевантность + реклама/шум
  summarization.py             # саммари принятого кластера
  digest.py                    # форматирование и лимиты Telegram
  delivery/telegram.py         # Bot API
  storage/base.py              # протокол Repository
  storage/tables.py            # SQLAlchemy Core metadata
  storage/postgres.py          # PostgresRepository и транзакции
  bot/handlers.py              # управление источниками/интересами в личке
  bot/app.py                   # постоянно работающий long-polling bot-worker
  orchestration/pipeline.py    # порядок шагов, retry, метрики прогона
  cli.py                       # run-pipeline, run-bot, validate-source
tests/
  unit/
  integration/
  fixtures/
```

Модули не передают друг другу произвольные `dict`: публичные границы используют модели
ниже. SQLAlchemy rows и запросы наружу из `storage` не выходят.

## Контракты данных

- `SourceConfig`: `id`, `kind`, `locator`, `collector`, `enabled`, `settings`,
  `cursor`. `collector` явно выбирает `native_rss`, `rss_bridge` или `telethon`, чтобы
  поведение не менялось от неявной эвристики во время прогона.
- `InterestProfile`: `id`, `name`, `description`, `enabled`, `version`, `created_at`,
  `updated_at`, `updated_by_telegram_user_id`. `description` — непустой свободный текст
  с одной или несколькими темами; система не заставляет пользователя раскладывать его по
  заранее заданной таксономии. Профиль относится к общей ленте/каналу, а не к отдельному
  читателю. Bot-worker позволяет посмотреть и заменить текст или включить/выключить
  профиль; каждое изменение атомарно увеличивает `version`. `pipeline-runner` фиксирует
  `id` и `version` профиля в снимке прогона, а `ClusterScreener` получает `description`
  без скрытого преобразования — так результат можно воспроизвести после редактирования.
- `RawItem`: `source_id`, `external_id`, `original_url`, `published_at`, `title?`,
  `raw_text?`, `raw_html?`, `attachments[]`, `metadata`. Это максимально близкий к
  источнику результат; неполные поля допустимы.
- `Attachment`: `kind`, `name`, `size?`, `download_ref?`, `mime_type?`. Отсутствующий
  `download_ref` у документа из RSS-Bridge — сигнал маршрутизировать источник в Telethon,
  а не пытаться извлекать пустое вложение.
- `Material`: `id`, `source_id`, `external_id`, `original_url`, `published_at`,
  `fetched_at`, `title`, `text`, `language?`, `content_hash`, `metadata`. `text` уже
  очищен от HTML и достаточен для дедупа/LLM; пустой текст запрещён.
- `NewsCluster`: `id`, `material_ids[]`, `representative_id`,
  `similarities{material_id: score}`. Все ссылки кластера сохраняются, даже если для
  промпта используется представитель.
- `ScreeningResult`: `cluster_id`, `relevance_score` и `noise_score` в диапазоне 0..1,
  `reason`, `model`, `prompt_version`. Решение `accepted` вычисляет наш код по порогам,
  а не LLM — тогда пороги можно менять без повторного вызова.
- `DigestItem`: `cluster_id`, `summary`, `source_links[]`, `model`, `prompt_version`.
  Список ссылок обязателен и содержит все материалы кластера.
- `DeliveryReceipt`: `digest_id`, `telegram_message_ids[]`, `sent_at`; пустой receipt не
  создаётся, если принятых кластеров нет.
- `RunReport`: `run_id`, времена начала/конца, счётчики по шагам, ошибки по источникам и
  стоимость/токены LLM. Ошибка одного источника не отменяет успешно собранные остальные.

## Модули пайплайна: вход и выход

| Шаг / модуль | Вход | Выход | Важный инвариант |
|---|---|---|---|
| 0. `Pipeline.load_context` | `run_id`, текущее время | активные `SourceConfig[]`, активный `InterestProfile`, пороги | Один транзакционно согласованный снимок конфигурации на весь прогон |
| 1. `SourceConnector.collect` | один `SourceConfig` + cursor | `CollectionBatch(raw_items[], next_cursor, errors[])` | Cursor не сохраняется до записи полученных items |
| 2. `IdentityDeduper` | `RawItem[]` + известные `(source_id, external_id/url)` | новые `RawItem[]`, ссылки на уже известные | Не скачивать статью/файл повторно |
| 3. `ContentExtractor` | новый `RawItem` и его attachments | `ExtractedItem(text, title, metadata)` или `ExtractionFailure` | PDF/DOCX и HTML дают обычный текст; скан без текста не идёт в LLM |
| 4. `Normalizer` | `RawItem` + `ExtractedItem` | валидный `Material` | URL канонизирован, время в UTC, HTML отсутствует, `content_hash` стабилен |
| 5. `ExactDeduper` | новые `Material[]` + сохранённые content hashes | уникальные `Material[]`, duplicate links | Дословная перепечатка отсекается до эмбеддингов |
| 6. `SemanticClusterer` | уникальные `Material[]` + материалы lookback-окна | `ClusterBatch(clusters[], duplicate_links[])` | SemHash `selected_with_duplicates` превращается в явные кластеры; порог конфигурируем |
| 7. `ClusterScreener` | один `NewsCluster`, его материалы, `InterestProfile.description` | один `ScreeningResult` | Ровно один LLM-вызов на кластер; реклама/шум и релевантность в одном JSON |
| 8. `ClusterSummarizer` | принятый кластер и все его материалы | один `DigestItem` | Ровно один вызов на прошедший кластер; ссылки не генерируются моделью, а добавляются кодом |
| 9. `DigestComposer` | `DigestItem[]`, локаль и лимиты Telegram | `Digest(posts[])` или `NoDigest` | Ноль прошедших кластеров означает штатную тишину; посты не превышают лимит API |
| 10. `TelegramDelivery.send` | `Digest` + channel id | `DeliveryReceipt` или типизированная ошибка | Повтор после сбоя не должен повторно публиковать уже подтверждённые части |
| 11. `Repository.finish_run` | результаты шагов, cursor-ы, receipt, `RunReport` | атомарно сохранённое состояние | Cursor и отметка доставки фиксируются только после соответствующего успеха |

`SourceConnector`, `LLMClient`, `Repository` и `DigestDelivery` оформляются как Python
`Protocol`. Для unit-тестов подставляются in-memory реализации; интеграционные тесты
работают на зафиксированных RSS/HTML/Telegram fixtures и отдельной тестовой Postgres-БД
(service container в CI, откат транзакции после теста).

### Идемпотентность и окна

- `Material.id` стабилен: хэш `(source_id, external_id)`, а при отсутствии external id —
  `(source_id, canonical_url)`; `content_hash` хранится отдельно.
- Для каждого источника хранится cursor (`published_at` + external id либо Telegram
  message id). Повторный прогон безопасен и не зависит только от даты из RSS.
- Семантический дедуп сравнивает новый материал как минимум с текущим batch и коротким
  lookback-окном сохранённых материалов; величина окна и threshold — конфигурация,
  которую надо откалибровать на первых реальных примерах.
- Результаты screening/summarization кешируются по `(cluster content hash,
  prompt_version, model)`. Изменение промпта не переиспользует старый ответ.
- LLM получает ограниченный по длине, детерминированно собранный текст. При слишком
  длинном PDF используется отдельный chunk/map-reduce extractor; это отдельная ветка
  внутри `ClusterSummarizer`, а не новый тип материала.

## Технические решения под бюджет ~$50
- **Планировщик**: GitHub Actions (cron). Бесплатных минут хватает на периодический запуск
  `pipeline-runner`. Он намеренно не переносится на VPS: прогон эпизодический, а локальные
  эмбеддинги/извлечение документов могут создавать пики CPU/RAM и не должны отнимать
  ресурсы у `rus-ai.com`. Постоянно на VPS работает только лёгкий `bot-worker`.
- **Хранилище**: отдельный Neon-проект AI News Feed с Postgres 18 и обязательным TLS.
  Провайдер тот же, что у `rus-ai.com`, но project id, connection string, роли, база и
  квоты отдельные; общую базу или schema двух приложений не используем. Доступ —
  через асинхронный SQLAlchemy 2 Core и `psycopg` 3 по собственному `DATABASE_URL`, схема
  меняется только миграциями Alembic. SQLAlchemy Core выбран вместо ORM: доменные
  Pydantic-контракты остаются независимыми от persistence-моделей, запросы и границы
  транзакций видны внутри `PostgresRepository`, а миграции всё равно получают единый
  `MetaData`. `psycopg` 3 — современный драйвер с нативным asyncio; одного драйвера
  достаточно обоим runtime-компонентам.
- **Управление источниками в боте**: инлайн-кнопки «Добавить источник» /
  «Посмотреть все источники» / «Удалить источник» (Telegram Bot API `InlineKeyboardMarkup`
  + `callback_query`). Тип источника (сайт или Telegram-канал) предлагается автоматически
  по формату ввода (URL или @handle), а фактически выбранный `collector` сохраняется в
  `SourceConfig`; так проверенный Telethon-маршрут не сменится обратно на RSS-Bridge.
  Таблица источников — с уникальным ограничением на нормализованный URL/handle, чтобы один
  источник нельзя было добавить дважды; у каждого источника свой id для управления.
- **Обработка команд бота**: отдельный `bot-worker` непрерывно выполняет Telegram long
  polling через `python-telegram-bot` и пишет источники и `InterestProfile` через тот же
  `PostgresRepository`, который читает пайплайн. Это даёт немедленный ответ без публичного
  URL, TLS/webhook-конфигурации и веб-фреймворка. Он разворачивается на имеющемся VPS как
  отдельный systemd-сервис с автоматическим restart; бесплатный PaaS для процесса не нужен.
- **Дедупликация**: сначала грубый хэш-фильтр на точные/почти точные повторы (перепечатки),
  затем [SemHash](https://github.com/MinishLab/semhash) — локальные эмбеддинги (Model2Vec)
  без платного API, для случая «та же новость другими словами» на разных сайтах.
- **Фильтр релевантности и рекламы/шума**: один LLM-вызов на кластер (не на статью),
  объединяющий две проверки — «это реклама/шум» и «это по теме интересов пользователя»
  (интересы — свободный текст, передаётся в промпт). Модель — самая дешёвая/быстрая из
  подходящих, это классификация, а не генерация. Результат — числовая оценка
  релевантности, а не только да/нет, чтобы порог можно было потом крутить без переделки
  шага. При сомнении лучше пропустить кластер дальше, чем отбросить — для узких тем
  пропущенная релевантная новость обходится дороже лишней в дайджесте. Если ни один
  кластер не прошёл — прогон завершается без отправки сообщения, это ожидаемое поведение.
- **Суммаризация**: один платный LLM-вызов на кластер, прошедший фильтр релевантности, а
  не на каждую статью — самый дорогой шаг, поэтому и самый чувствительный к контролю
  стоимости; лишних вызовов дорогой модели на нерелевантные кластеры при этом не будет.
- **Доставка**: приватный Telegram-канал — бот добавлен админом с правом публикации и
  постит дайджесты из `pipeline-runner` (bot-worker для доставки не нужен). К каналу
  привязана группа-обсуждение (Discussion) — даёт комментарии под постами штатной функцией
  Telegram, без своей разработки. Если бот должен ещё и читать комментарии (например, как
  сигнал для ранжирования в будущем) — добавить его и в группу-обсуждение, и отключить
  Privacy Mode через @BotFather (`/setprivacy`) до того, как он туда добавлен.
- **Источники**: нативный RSS читается напрямую. RSS-Bridge используется как внешний
  адаптер для сайтов без RSS и обычных публичных Telegram-каналов; Python получает его
  Atom/RSS-выдачу через тот же `feedparser`. Для источников, где веб-превью пусто или
  нужны скачиваемые документы, `collector=telethon` выбирается сразу, а не после тихого
  fallback внутри прогона.
- **Вложения-документы в Telegram (PDF/DOCX-отчёты)**: у части каналов (например,
  аналитика по рынку ИИ) контент лежит не в тексте поста, а во вложенном файле.
  RSS-Bridge отдаёт только имя и размер файла, не сам файл — для таких каналов нужен
  Telethon: скачать документ и извлечь текст (PDF — `pdfplumber`/PyMuPDF, DOCX —
  `python-docx`), дальше этот текст идёт в тот же фильтр релевантности и суммаризацию,
  что и обычная статья. Для длинных отчётов, возможно, понадобится отдельный промпт
  суммаризации (ключевые цифры/выводы, а не пересказ в одну строку) — решим по факту
  первых тестов.

## Проверка источников ★ (31.08.2026)
Docker недоступен локально на Mac PO — вместо разворачивания RSS-Bridge через него,
проверили напрямую тот же механизм, что использует RSS-Bridge (публичное веб-превью
`t.me/s/<канал>` и HTML/RSS сайтов). RSS-Bridge остаётся в плане для продакшена — на
раннерах GitHub Actions Docker есть по умолчанию, локальный Docker для этого не нужен.

Находки:
- **@ailev_blog** (обычный текстовый канал) — веб-превью отдаёт полный текст постов.
  Подход «RSS-Bridge / веб-превью» подтверждён для этого типа каналов.
- **@expertosphere** — веб-превью (`t.me/s/expertosphere`) не отдаёт посты вообще, только
  шапку канала («Preview channel / View in Telegram») — ни через прямой фетч, ни через
  обычный браузер. Это сильнее исходной находки про вложения (RSS-Bridge отдал бы только
  имя/размер файла, не содержимое) — для этого канала Telethon нужен не как опция для
  вложений, а как единственный рабочий способ вообще получать посты.
- **ict.moscow/analytics** — нативного RSS нет, нужен универсальный CSS-selector-бридж
  RSS-Bridge или свой скрапер.
- **tadviser.ru** — есть RSS: `https://www.tadviser.ru/xml/tadviser.xml` (общий по всему
  сайту, не только по ИИ) — можно читать напрямую (`feedparser`), фильтрация по теме всё
  равно идёт через шаг релевантности. Отдельно: прямой фетч этой страницы через
  автоматический HTTP-клиент вернул 403 (похоже на блокировку по User-Agent/IP), обычный
  браузер открыл страницу без проблем — см. риск ниже.
- **issek.hse.ru/ai** — есть RSS, но общий по организации:
  `https://www.hse.ru/rss/orgs/70333/news_and_announcements.rss`, не только по серии «ИИ» —
  тоже читаем напрямую, фильтруем релевантностью.

## Сверка с auto-news и RSS-Bridge (31.08.2026)

Бегло просмотрены `main` и ключевые файлы
[auto-news](https://github.com/finaldie/auto-news): `dags/news_pulling.py`,
`src/af_pull.py`, `src/af_save.py`, `src/ops_rss.py`, `src/llm_agent.py`,
`src/llm_prompts.py` и `pyproject.toml`.

Что берём как референс:

- явные стадии `pull → process/save → publish`, отдельный `run_id` и сохраняемые JSON
  между стадиями — полезный образец наблюдаемости и повторного запуска;
- одинаковый жизненный цикл источников и отдельные source operators;
- кеширование LLM-ответов и сохранение статистики прогона;
- дешёвый pre-filter до LLM для источников с большим потоком.

Что намеренно не переносим:

- Airflow, Notion, Redis, Milvus/Chroma, LangChain/LlamaIndex и десятки опциональных
  зависимостей: это оправдано масштабом auto-news, но слишком тяжело для нашего личного
  cron-процесса и бюджета;
- source operator, который одновременно получает, дедуплицирует, суммаризирует,
  ранжирует и публикует. У нас эти обязанности разделены общими модулями и контрактами;
- обработку RSS независимо от Telegram и документов: наш единый `Material` нужен именно
  затем, чтобы downstream не знал способ получения;
- суммаризацию отдельных статей. В нашем PRD сначала формируется кластер, затем выполняются
  один screening-вызов и один summary-вызов на прошедший кластер.

По исходникам [RSS-Bridge](https://github.com/RSS-Bridge/rss-bridge) подтверждено:

- `TelegramBridge` строит URL `https://t.me/s/<username>`, парсит доступные в публичном
  превью сообщения и выдаёт `uri`, `title`, `content`, `timestamp`, `author`,
  `enclosures`; его часовой cache не делает недоступный пост доступным;
- если `t.me/s/...` не отдаёт элементы сообщений, bridge тоже не сможет получить посты.
  Поэтому проверенный пустой preview `@expertosphere` однозначно маршрутизируется в
  Telethon;
- `processAttachment()` действительно добавляет только имя документа и дополнительную
  строку вроде размера, без URL скачивания. Для извлечения PDF/DOCX нужен Telethon;
- `CssSelectorBridge` может найти ссылки CSS-селектором и опционально сходить на каждую
  страницу за полным контентом. Это подходит для `ict.moscow`, но селекторы хрупкие, а
  расширение каждой статьи медленнее; конфигурация селекторов должна храниться в
  `SourceConfig.settings` и проверяться интеграционным fixture-тестом.

Итог сверки: RSS-Bridge остаётся адаптером только там, где его выдача проверена;
Telethon — полноценный коннектор, а не аварийная деталь внутри RSS-коннектора. Из
auto-news заимствуем контрольные точки и метрики, но оставляем линейный лёгкий рантайм.

## Эксплуатационная топология

### Общее состояние: отдельный Neon-проект

Создаётся новый Neon-проект **AI News Feed** с Postgres 18 и TLS. Он находится у того же
провайдера, что и база `rus-ai.com`, но не использует её project id, connection string,
database, role или schema. Такая граница исключает случайные миграции/удаления данных
рабочего сервиса и позволяет независимо удалить, восстановить или перенести пет-проект.

На [Neon Free](https://neon.com/pricing) лимиты считаются на проект: AI News Feed получает
собственные 100 CU-часов в месяц и 0,5 ГБ storage, не расходуя квоту проекта `rus-ai.com`.
Для ожидаемого объёма MVP этого достаточно и стоимость остаётся $0, пока проект
укладывается в лимиты; usage проверяется отдельно в Neon Console. Оба runtime-компонента
получают connection string нового проекта через свой secret `DATABASE_URL` и требуют TLS.

`bot-worker` выполняет короткие транзакции изменения источников/интересов, а
`pipeline-runner` в начале прогона читает согласованный снимок конфигурации и дальше
сохраняет материалы, кластеры, решения и доставку через тот же `PostgresRepository`.
Миграции Alembic запускаются отдельной командой до старта новой версии приложения, не
автоматически из двух процессов. Для bot-worker используется маленький connection pool
с `pool_pre_ping`; конечный pipeline-runner не держит соединения после завершения.

### Bot-worker: systemd на VPS

`bot-worker` размещается на имеющемся VPS (Ubuntu 24.04, 2 vCPU, 4 ГБ RAM, 50 ГБ SSD),
где уже работает `rus-ai.com` (Streamlit + Nginx + HTTPS). Long polling не открывает
входящий HTTP-порт, поэтому бот не меняет Nginx-конфигурацию и не использует домен или
TLS-сертификаты `rus-ai.com`.

Изоляция deployment:

- отдельный непривилегированный OS-пользователь без login shell и sudo, например
  `ai-news-feed`; сервис не запускается от root и не использует пользователя Streamlit;
- отдельный каталог приложения и собственный virtualenv, не общий с Streamlit-проектом;
- отдельный unit `/etc/systemd/system/ai-news-feed-bot.service` с `User=ai-news-feed`,
  своим `WorkingDirectory`/`EnvironmentFile`, `Wants`/`After=network-online.target`,
  `Restart=always`, `RestartSec` и `WantedBy=multi-user.target`; unit включён через
  `systemctl enable`;
- bot token и Neon `DATABASE_URL` лежат в отдельном root-owned environment-файле с
  минимальными правами, не в репозитории и не в unit-файле;
- stdout/stderr идут в journald; deploy/restart бота не перезапускает unit Streamlit.

Для одного bot token работает ровно одна активная реплика bot-worker; webhook отключён,
а offset подтверждённых updates ведёт `python-telegram-bot`. Сервис сразу отвечает на
callback-кнопки и транзакционно обновляет `SourceConfig`/`InterestProfile`. Дубли
источников блокирует уникальный индекс по нормализованному locator, потерянные обновления
профиля — поле `version`.

Systemd restart-policy и собственный VPS закрывают прежний риск, что бесплатный хостинг
усыпит polling-процесс. Остаются обычные риски самого VPS: reboot, нехватка ресурсов и
сетевой сбой. Telegram хранит неполученные updates не дольше 24 часов, поэтому после
перезагрузки unit должен подниматься автоматически. Чтобы защищать `rus-ai.com`, bot-worker
не импортирует ML-модули pipeline-runner; после измерений unit можно ограничить через
systemd `MemoryMax`/`CPUQuota`.

### Pipeline-runner: только GitHub Actions

Периодический `pipeline-runner` остаётся в GitHub Actions и **не запускается на VPS**.
Это эпизодическая batch-задача, которой не нужен daemon/systemd, зато извлечение PDF и
локальные эмбеддинги могут кратковременно нагружать CPU/RAM. GitHub runner принимает эти
пики на себя и не конкурирует со Streamlit/Nginx за 2 vCPU и 4 ГБ RAM VPS.

Workflow получает отдельный Neon `DATABASE_URL`, Telegram/Telethon secrets, выполняет
один идемпотентный прогон и завершается. VPS хранит только лёгкий bot-worker; код и
`Repository` у двух компонентов общие, а runtime и deployment независимы.

### Открытый вопрос: как запускать RSS-Bridge

1. **Эфемерный контейнер внутри workflow** — контролируемая версия и нет внешнего сервиса;
   минусы: startup на каждом прогоне и отсутствие долговечного cache. Рекомендуется для
   первых интеграционных прогонов при малом числе источников.
2. **Публичный instance** — нулевая инфраструктура; минусы: лимиты, приватность списка
   источников и отсутствие SLA. Только для ручной проверки, не как production dependency.
3. **Постоянный self-hosted instance** — работает cache и быстрее повторные запросы;
   минус: возвращает постоянно работающий сервер, которого MVP старается избежать.

Если эфемерный контейнер окажется дороже по минутам или начнёт провоцировать блокировки
без cache, для одного-двух сайтов рациональнее заменить только их на небольшой Python-
скрапер за тем же `SourceConnector`, не менять остальной пайплайн.

## Что осознанно откладываем
- Векторную БД/pgvector (эмбеддинги и их метаданные хранятся в обычном Postgres,
  поиск и SemHash выполняются локально в pipeline-runner).
- HTTP API и веб-интерфейс (bot-worker использует long polling, pipeline-runner — CLI).
- YouTube/VK-коннекторы и FB-Pages — Фаза 2. FB-группы — не планируем без пересмотра.
- Персонализацию/ранжирование сверх базового — при канале на нескольких человек все видят
  одну и ту же ленту; разная персонализация под разных людей означала бы отдельные каналы.

## Фаза 2 (после MVP)
- **Репост оригинала по метрикам**: помимо дайджеста — прямая ретрансляция поста из
  источника без изменений (`forwardMessage`, сохраняет атрибуцию, либо `copyMessage` +
  ссылка вручную), если просмотры/реакции оригинала выше заданного порога. Метрики
  читаются тем же способом, что и сам контент источника (Telethon/RSS-Bridge) — отдельный
  механизм не нужен.
- **Персонализация по реакциям**: реакции на посты бота читаются через Bot API —
  `message_reaction` в личке/группе (с привязкой к человеку), `message_reaction_count` в
  каналах (только агрегированное число, анонимно). Пока канал на одного человека, этого
  достаточно; если канал станет общим на нескольких людей — привязать реакцию к
  конкретному человеку в канале Telegram не даёт, персонализация на уровне человека в общем
  канале технически не реализуема. Начинаем с простого: вектор предпочтений = взвешенное
  среднее эмбеддингов лайкнутых минус дизлайкнутых кластеров (те же эмбеддинги, что и для
  дедупа), новые кандидаты оцениваются косинусным сходством с этим вектором — без новых
  зависимостей. Более серьёзные варианты, если понадобятся, — в RESEARCH.md (rss-swipr,
  river).

## Риски, за которыми стоит следить
- Отдельный Neon-проект изолирует AI News Feed от `rus-ai.com`, но имеет собственные
  бесплатные лимиты 100 CU-часов/месяц и 0,5 ГБ. Следить за usage и ростом материалов;
  превышение квоты или изменение условий тарифа не должно обнаруживаться только по
  упавшему cron. Scale-to-zero может добавить задержку первому запросу после простоя.
- VPS остаётся общей физической точкой для bot-worker и `rus-ai.com`: контролировать RAM,
  CPU, SSD и размер journald. Bot-worker не должен загружать SemHash/модели; при
  необходимости зафиксировать `MemoryMax`/`CPUQuota`, не ухудшая отзывчивость бота.
- VPS/reboot/сеть — единая точка отказа bot-worker. Unit должен быть `enabled`, иметь
  restart-policy и проверяться простым health-check/алертом; простой дольше окна хранения
  Telegram updates может потерять команды. Риск «бесплатный хостинг усыпил процесс» снят,
  поскольку polling работает на собственном VPS.
- Ошибка прав или утечка environment-файла не должна давать доступ к `rus-ai.com`:
  отдельные OS-user, каталоги, Neon project/role и secrets обязательны, backup и миграции
  AI News Feed выполняются независимо.
- Чтение Telegram через пользовательский аккаунт технически может попадать под
  ограничения Telegram на автоматизацию — риск для личного аккаунта, стоит свериться
  с актуальными правилами перед тем, как полагаться на это постоянно.
- VK может изменить условия API без предупреждения.
- Парсинг сайтов без RSS менее стабилен, чем официальные API.
- Рост стоимости LLM-вызовов при увеличении числа источников — контролировать
  суммаризацией по кластерам и дешёвыми моделями на шаге дедупа/фильтрации.
- Некоторые сайты блокируют автоматические HTTP-клиенты (tadviser.ru вернул 403
  прокси-фетчеру, но открылся в обычном браузере) — если повторится в проде (GitHub
  Actions), может понадобиться другой User-Agent, задержки между запросами или
  headless-браузер вместо простого HTTP-запроса. Проверить на первом реальном прогоне.
